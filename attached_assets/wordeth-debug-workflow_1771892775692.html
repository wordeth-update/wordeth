server.js
Server detects real user, serves verses.html
The GET /room/:roomId handler checks the User-Agent. If not a crawler bot, it calls res.sendFile('verses.html'). OG meta tags are served only to bots.
Room ID correctly extracted from URL path (no query param bleed)
6
verses.js — bottom IIFE + AudioRoomsManager constructor
verses.html loads → two DOMContentLoaded listeners race
The IIFE at the bottom of verses.js and the class initialization both attach to DOMContentLoaded. The IIFE polls for window.audioRoomsManager every 100ms. If the manager initializes fast (socket connects fast), the IIFE may run AFTER _init() has already completed and moved on — meaning the pending room invite is never queued.
🐛 Race condition: invite lost if manager inits before IIFE detects it ✓ Fix: queueInvite() in constructor if URL has room param
7
verses.js — connectToServer()
Socket connects → _processInvite() guard is broken
Inside the connect event handler in connectToServer(), the guard this._initComplete && this._invite.status === 'pending' will always be false at that moment because _initComplete is only set after await connectToServer() returns in _init(). The code in _init() handles this as a fallback — but the dead guard creates confusing control flow that makes debugging very hard.
🐛 Dead guard: _initComplete always false in connect handler ⚠ Works via fallback in _init() but creates unpredictable ordering
!
server.js + signaling.js
🔴 CRITICAL: Room state lives in memory only
const rooms = new Map() in signaling.js is module-level. Any Railway deployment, crash, or server restart wipes all active rooms. The invitee navigates to the room URL, the socket connects, emits join-room — but the room no longer exists. Server returns room-error: "This room is no longer live." This is likely the primary cause of failed invite joins in production.
🐛 Server restart = all rooms vanish ✓ Fix: Replace Map with Redis (ioredis + TTL per room)
9
server.js Socket.io init vs verses.js connectToServer()
Transport config mismatch causes connection overhead
The server initializes Socket.io with transports: ['polling', 'websocket'] (polling first). The verses.js client uses transports: ['websocket', 'polling'] (WebSocket first). Behind Cloudflare, WebSocket upgrades can fail silently, causing the client to fall back to polling — then attempt upgrade again — adding 200-600ms latency before any room join logic begins.
🐛 Mismatch: server=polling→WS, client=WS→polling ✓ Fix: Both server + client should use ['websocket'] only on Railway/CF
10
verses.js + signaling.js + agora
join-room → room-joined → Agora join
Once the socket is connected and join-room is emitted, the server validates room existence, adds the participant, and emits room-joined back. The client then calls _agoraJoinGuarded() which fetches an Agora token and joins the RTC channel. This sequence itself is well-implemented with the lock guard.
5s timeout guards against hung joins Agora join happens AFTER room-joined confirmation — correct
BUGS — RANKED BY IMPACT
🔴 Critical
In-Memory Room State (signaling.js)
const rooms = new Map() is ephemeral. Railway restarts (deploys, crashes, memory limits, sleep) destroy all rooms. The invitee follows the link to a ghost room.
// signaling.js — line 1
const rooms = new Map(); // ← dies on restart

// Fix: use Redis with TTL
const redis = new Redis(process.env.REDIS_URL);
// Store rooms as JSON with EXPIRE 3600 (1hr)
Fix: Add a Redis instance on Railway (Redis service, $5/mo). Use ioredis. Store room state as JSON strings with a 1-hour TTL. On room close/empty, explicitly delete the key.
🟡 High
Socket Transport Mismatch (server.js vs verses.js)
Server is configured polling-first; the verses.js client is WebSocket-first. Cloudflare may reject the WS upgrade on the first attempt, causing a retry cycle that adds 200–600ms before the join can begin.
// server.js — Socket.io init
transports: ['polling', 'websocket']

// verses.js — connectToServer()
transports: ['websocket', 'polling']

// Fix: match both to WebSocket-only
transports: ['websocket']
Fix: Set both server and all clients to transports: ['websocket']. Cloudflare supports WebSocket on all plans. Remove polling entirely — it requires sticky sessions which Railway doesn't guarantee by default.
🟡 High
Race: Manager Init vs IIFE queueInvite (verses.js)
The bottom IIFE polls for window.audioRoomsManager every 100ms. If the socket connects very fast on a good network, _init() completes before the IIFE's first poll fires — so _invite.status is never set to 'pending' before _init() finishes, and no join is triggered.
// Current: IIFE waits for manager to exist
const waitForManager = (attempt = 0) => { ... }

// Fix: parse room from URL in constructor
constructor() {
const urlRoom = this._parseRoomFromUrl();
if (urlRoom) this.queueInvite(urlRoom);
// ...rest of constructor
}
Fix: Parse the room ID from the URL inside the constructor before calling _init(). This eliminates the race entirely — the invite is queued synchronously before any async work begins.
🟡 High
register-user Not Re-emitted on Reconnect (verses.js)
The register-user event is emitted only in the first connect handler in connectToServer(). If Cloudflare drops the WebSocket (100s timeout on inactivity), the socket reconnects but register-user is NOT re-emitted. The server's connectedUsers Map now has a stale socket ID, so future invites are sent to a dead socket.
// Missing: re-register on reconnect
this.lobbySocket.on('connect', () => {
// This fires on EVERY connect + reconnect
this.lobbySocket.emit('register-user', {...})
}); // ← Already here! But also need:

// Add in connectSocket() reuse path:
if (lobbySocket.connected) {
lobbySocket.emit('register-user', user);
}
Fix: The on('connect') handler in connectToServer() already re-emits on reconnect (Socket.io fires 'connect' on reconnects too). But connectSocket() skips this path when reusing a connected socket. Add a register-user emit in the connectSocket() reuse branch.
🔵 Medium
Dead Guard in connectToServer() (verses.js)
Inside the connect handler, the condition this._initComplete && ... is always false because _initComplete is set after await connectToServer() resolves. The code works (via the _init() fallback) but the dead branch creates confusing debugging paths and hides real state.
lobbySocket.on('connect', () => {
resolve();
// This condition is ALWAYS false here:
if (this._invite.status === 'pending'
&& this._initComplete ← always false
&& !this.currentRoom) {
this._processInvite();
}
});
Fix: Remove the _initComplete guard from the connect handler. The _init() method already handles _processInvite() after the await. Simplify to just resolve() + register-user emit.
🔵 Medium
Cloudflare WebSocket + Railway: No Sticky Sessions
If Wordeth ever scales to multiple Railway instances, Socket.io's polling fallback requires sticky sessions (same backend server per client). Without this, polling requests go to different instances that don't share the socket handshake state. WebSocket-only mode eliminates this entirely.
// Cloudflare → Railway without sticky sessions
// HTTP polling requests can hit different instances
// = handshake fails = no socket = no join

// Solution: WebSocket-only (no polling fallback)
// Cloudflare handles WS on all plans
// Railway single instance is fine for now
Fix (now): Switch to WebSocket-only transport. Fix (later, at scale): Add Redis adapter for Socket.io (@socket.io/redis-adapter) so multiple Railway instances share socket state through the same Redis instance.
IMPLEMENTATION CHECKLIST — IN ORDER
P1 NOW

Add Redis to Railway & update signaling.js

Provision a Redis service on Railway. Replace const rooms = new Map() with ioredis calls. Store room state as JSON with SETEX roomId 3600 json. This single change fixes the most common production failure (server restart → dead invite link).

P1 NOW

Set WebSocket-only transport on server and ALL clients

In server.js new Server() options, set transports: ['websocket']. Do the same in verses.js connectToServer() and notifications.js socket init. Verify Cloudflare's "WebSockets" toggle is ON in the Network settings for your domain.

P1 NOW

Move room URL parsing into AudioRoomsManager constructor (before _init)

Extract the room-from-URL logic from the bottom IIFE into a _parseRoomFromUrl() method. Call this.queueInvite(roomId) synchronously in the constructor, before this._init(). Delete the polling waitForManager IIFE — it's no longer needed.

P2 NEXT

Add register-user re-emit in connectSocket() reuse path

In verses.js connectSocket(), when lobbySocket is already connected, add a lobbySocket.emit('register-user', ...) call. This ensures the server's connectedUsers map is always fresh after reconnects or navigation.

P2 NEXT

Remove the dead _initComplete guard from the connect handler

Simplify connectToServer()'s on('connect', ...) to only: call resolve(), emit register-user, and update rooms display. Remove the _processInvite() call from there — _init() already handles it correctly.

P2 NEXT

Add @socket.io/redis-adapter for horizontal scalability

Install the adapter and pass your Redis client to io.adapter(createAdapter(pubClient, subClient)). This ensures socket events (like rooms-updated) broadcast across all Railway instances. Not blocking today, but essential before scaling past 1 server.

P3 LATER

Add Cloudflare Worker or health-ping to keep Railway from sleeping

Railway may put your service to sleep on inactivity (depending on plan). A cron-based ping every 5 minutes prevents cold starts. Alternatively, upgrade to a paid Railway plan with "Always On" instances. This also prevents Cloudflare's 100s WebSocket timeout from killing idle connections.

P3 LATER

Add join-room retry with exponential backoff

Currently, if join-room is emitted but no room-joined arrives within 5s, the flow fails silently. Add an explicit retry: re-emit join-room after 2s if no response, before giving up at 5s. Useful for temporary Cloudflare hiccups.

P3 LATER

Wire server-side invite delivery confirmation back to host

Currently, if the invitee's socket has gone stale, the host sees "Invite sent" but the invitee never receives it. Use the existing invite-sent event to show a real-time "User is offline — link copied" fallback in the host UI instead of the generic fallbackInvite().
