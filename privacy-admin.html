Cookie Consent: How It Works

A small banner slides up from the bottom of every page the first time someone visits. Two options:

  • Accept All — enables full analytics tracking alongside essential site functionality
  • Essential Only — site works normally, but analytics events are silently skipped (the tracking call returns immediately without saving data)

The choice is stored in the browser's localStorage under the key wordeth_cookie_consent. It includes a version number so if you update the privacy policy, you can bump the version to re-prompt users.

Version Bump

To re-prompt all users after a policy update, change CONSENT_VERSION in js/cookie-consent.js. Any stored consent with an older version will trigger the banner again.

Tracking & Consent

Wordeth has two layers of tracking:

  1. Server-side middleware (middleware/tracking.js) — Automatically logs API route usage. This is operational/essential tracking and is not affected by the cookie banner. It tracks which endpoints are called, not personal browsing behavior.
  2. Client-side tracking (POST /api/analytics/track) — Used for things like Verses join/leave events. This endpoint checks the consentGiven field in the request body. If consentGiven is false, the event is silently skipped.
How consent flows

The cookie consent JS sets a flag that client-side tracking code reads before making requests. If consent was declined, the tracking call sends consentGiven: false and the server returns immediately without storing anything.

Terms & Signup Enforcement

During account creation on signup.html:

  1. A checkbox appears: "I agree to the Terms of Service and Privacy Policy" (with links to both documents)
  2. The signup button is disabled until the box is checked (client-side)
  3. The server also validates agreedToTerms: true in the request body and rejects signups without it (server-side)
Social Login

Social OAuth logins (Twitter, Instagram, Facebook) are currently marked "Coming Soon" and are non-functional. When they are activated in the future, terms enforcement should be added to those flows as well.

Terms Agreement Data

When a user agrees to terms during signup, these fields are saved on their User record in MongoDB:

{
  "agreedToTerms": true,
  "termsAgreedAt": "2026-02-07T14:30:00.000Z",
  "termsVersion": "1.0"
}

This provides an audit trail for compliance: you can verify when each user agreed and to which version of the terms.

Data Flush: What Gets Deleted

When a data flush is performed (by admin or by the user themselves), the following is permanently removed:

  • User account — The entire User document including name, email, password hash, and all embedded data (search history, annotations, custom merch designs)
  • Usage tracking events — All records in the UsageEvent collection tied to that user
  • Social connections — The user is removed from all other users' followers and following lists
  • Uploaded files — Avatar images stored on the server are deleted from disk
Irreversible

Data flush is permanent and cannot be undone. There is no recycle bin or grace period. Always double-check the email before confirming.

Admin Flush via API

This is for your team to handle user data deletion requests (e.g., GDPR "Right to Erasure" requests sent via email or support ticket).

Step 1: Get an Admin Token

Sign into the Admin panel with your admin credentials. The admin system uses the same authentication. You'll need the JWT token from that login.

To get your token programmatically:

POST /api/ads/admin/login
Content-Type: application/json

{
  "email": "your-admin@wordeth.com",
  "password": "your-admin-password"
}

The response includes a token field — that's your admin JWT.

Step 2: Call the Flush Endpoint

POST /api/user/admin/flush
Authorization: Bearer YOUR_ADMIN_TOKEN
Content-Type: application/json

{
  "email": "user-to-delete@example.com"
}

Step 3: Review the Response

A successful flush returns details of everything that was removed:

{
  "success": true,
  "message": "User data has been permanently deleted",
  "details": {
    "email": "user@example.com",
    "name": "Jane Doe",
    "deletedData": {
      "usageEvents": 47,
      "followersRemoved": 3,
      "followingRemoved": 5,
      "avatarRemoved": true,
      "accountDeleted": true
    },
    "flushedAt": "2026-02-07T15:00:00.000Z"
  }
}

User Self-Delete

Users can delete their own account by calling this endpoint with their regular login token:

DELETE /api/user/account
Authorization: Bearer USER_JWT_TOKEN

This performs the same complete data removal as the admin flush. The response confirms deletion:

{
  "success": true,
  "message": "Your account and all associated data have been permanently deleted"
}
Future Enhancement

Consider adding a "Delete My Account" button to the user profile page that calls this endpoint, so users can self-serve without contacting support.
